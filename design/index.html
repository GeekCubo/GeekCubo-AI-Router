Routing strategy

How the router picks between candidate models when you send model="auto".

    Pick a card to switch strategy. Saved immediately.

    How Auto routing works — setup, checks and switching off
    1. Use Auto: send model="auto" from an SDK, or pick Auto (router picks) in the Chat model menu. Any other model id (for example my-provider/gpt-4o) is pinned and bypasses Auto.
    2. Make a model eligible: under Providers the provider must be enabled and Included in Auto, the model enabled, and it needs a confirmed price (a custom $ in/out). Reference estimates count only if you allow them in Pricing below. The Availability column in the pool table shows each model's state.
    3. Keep a model out of Auto: disable the model, choose Exclude from Auto on its provider (it stays usable when pinned), or clear its price.
    4. Strategy: click a card above; it applies to the next request. Pools only matter for Adaptive-Gated (and for escalation); other strategies rank every eligible model.
    5. Why this model?: use Test a routing decision below, or read the x-geek-routing-* response headers; Analytics → Recent requests shows the routed model for every call.
    6. Nothing eligible: the request fails with a 422 that names the blocker (no price, missing capability, empty pool, context too long) instead of guessing a model.
    7. Stop a reply in Chat with the Stop button (it replaces Send while generating); the partial answer is kept.

    Auto model routing is separate from the reserved Auto web search mode in Chat settings, which is not implemented.

    Model pools

    Pick from models registered here. Adaptive-Gated routes Mundane requests to the mundane pool and Hard requests (tools, images, long prompts) to the hard pool. The Fallback pool catches a tier that cannot serve a request.

    Fallback, escalation & continuity

    Fallback and escalation always keep the request's required capabilities. Decisions are made before a request starts; models never change mid-stream.

    Fallback
    What counts as retryable

    Rate limits, timeouts, connection errors, upstream 5xx and unknown-model 404s move to the next candidate. Authentication, permission, malformed-request and content-policy errors stop immediately — retrying them just burns the same failure on another provider.

    Balanced
    What the quality floor does

    Balanced weighs price against quality. The floor excludes models below that percentile, so a very cheap but weak model cannot win. Set it to 0 to disable the floor entirely.

    Hard request signals
    How request signals are measured

    A request enters the Hard pool when it matches any enabled signal here: a tool schema, an image part, more than the message threshold, or a prompt longer than the character threshold. All four are independent — turn on only the ones that actually predict a harder task for your traffic.

    Escalation
    When escalation triggers

    Escalation reacts to observed upstream failures, or to an explicit x-geek-escalate signal from the client. It never guesses at answer quality, so a cheap model that answers well stays put.

    Continuity
    What continuity does

    Routing each message independently breaks prompt caches: the same conversation bounces between models and every turn pays full input price. Stickiness pins a conversation to the model it already used, for the window above.

    Pricing Off by default. Only confirmed provider prices are compared; models with only a reference estimate stay out of Auto. When on, every estimate-based decision is labelled.

    Test a routing decision

    Dry-run: shows which model Auto would choose and why. Nothing is sent upstream.

    How model="auto" works

    Three filters, applied in order.

    1. Capability filter. The router inspects your request — is there an image? a tool definition? response_format=json? — and drops models that can't handle it.
    2. Provider filter. Only models whose provider you've configured survive.
    3. Strategy ranking. The remaining candidates are scored by your chosen strategy above. The winner is called.

    The chosen model comes back to your client in the x-geek-resolved-model response header. The routing decision is echoed as x-geek-routing-strategy, x-geek-routing-profile and x-geek-routing-effective. x-geek-routing-strategy is still sent for clients that already read it.

    How each strategy maps to LiteLLM Router
    Strategy litellm routing_strategy model="auto" picks
    balancedNone (we rank ourselves)50/50 normalized AA quality & inverted cost; strict two-axis coverage
    cheapestcost-based-routingcheapest capable (blended 0.3 input + 0.7 output cost)
    fastestNone (we rank ourselves)50/50 normalized AA TPS & inverted TTFT; strict two-axis coverage
    qualityNone (we rank ourselves)highest AA Intelligence Index (or manual override); unscored models rank below scored

    The strategy controls two things: which model model="auto" resolves to, and how LiteLLM Router picks between deployments that serve the same model (e.g. multiple configured provider keys).

              How quality scoring works
              
                    
                
                      
                  
                    1. Sign up at artificialanalysis.ai and generate an API key on the account page. The account page also states that key's request allowance.
                      2. 
                  
                    2. Paste it above and save. It is encrypted at rest, and anything already cached is discarded so the next refresh uses the new key.
                      3. 
                  
                    3. Click Test connection, then Refresh from AA on the Quality scores tab. Scores then update on their own: results are cached for an hour and survive restarts.
                      4. 
                
                    
                
                    
                  Without a key, quality falls back to the legacy cost-based behavior. cheapest / balanced / fastest are unaffected. Manual overrides on the Models tab work without any AA key and take precedence when present.
                
                    
              
                    
            
                    
            
                    
              Connection troubleshooting
              
                    
                
                      
                  
                    • Invalid key (401): the key was mistyped, revoked, or regenerated. Regenerating a key on Artificial Analysis revokes the old one immediately; paste the new key with Replace key.
                      • 
                  
                    • Plan does not include this endpoint (403): GeekCubo uses the Free language-models endpoint, which every key can call. A 403 there usually means the key belongs to an organization without API access.
                      • 
                  
                    • Endpoint retired (410): an old GeekCubo build or a custom ARTIFICIAL_ANALYSIS_MODELS_URL still points at the retired /api/v2/data/ API. Update GeekCubo or remove the override.
                      • 
                  
                    • Rate limited (429): Free keys have 100 requests per 24-hour window. A test uses one request; a sync uses one per page (about four). The quota resets in full when the window ends.
                      • 
                  
                    • Timeout or network error: the server could not reach artificialanalysis.ai over HTTPS. Check outbound network access and DNS.
